# Requirements taxonomy reference

Classification codes, NFR categories with measurable metrics, and requirement-quality rules for every `requirements-collector` document.

## Classification codes

| Code | Название | Что описывает | Пример |
|------|----------|---------------|--------|
| BR | Бизнес-требование | зачем, ценность, KPI, эффект | «Сократить время обработки заявки на 30%» |
| StR | Требование стейкхолдера | что конкретный стейкхолдер хочет | «Финконтроль требует аудит-лог всех изменений» |
| FR | Функциональное | что система должна делать | «Система отправляет уведомление по email» |
| NFR | Нефункциональное | как система должна работать | «p95 latency ≤ 300 мс» |
| BRU | Бизнес-правило | условие → действие | «Сумма > 100 000 ₽ → согласование руководителем» |
| CON | Ограничение | рамки, в которых делаем | «Только PostgreSQL 16» |
| ASM | Допущение | принято без подтверждения | `[предположение]` «Нагрузка до 100 RPS» |
| DEP | Зависимость | внешнее, без чего нельзя | «API поставщика доступен с 01.06» |
| INT | Интерфейс/интеграция | точка обмена с внешним миром | «REST OUT → CRM» |
| DAT | Данные | сущности, потоки, хранение | «Заявка: 50 полей, JSON, 10k/день» |
| RISK | Риск | неопределённость с оценкой | см. risk-model.md |
| GLOSS | Глоссарий | термин и его однозначное определение | «Активный пользователь = вошёл и совершил действие за 30 дней» |

## NFR categories and measurable metrics

Every NFR must state its category and a measurable metric.

| Категория | Метрики |
|-----------|---------|
| Производительность | latency (p50/p95/p99), throughput (RPS), response time, TTFB |
| Масштабируемость | макс. нагрузка (RPS/пользователей), рост данных (ГБ/мес), горизонтальное масштабирование (узлы) |
| Доступность | SLA (%), uptime, RTO, RPO |
| Надёжность и отказоустойчивость | MTBF, MTTR, число «9», graceful degradation |
| Безопасность | аутентификация (MFA), авторизация (RBAC), шифрование (TLS 1.3, AES-256), аудит (логируемые события) |
| Compliance | GDPR, 152-ФЗ, PCI DSS, отраслевые нормы |
| UX и доступность | WCAG 2.1 AA, время выполнения задачи, локализация (языки) |
| Сопровождаемость, тестируемость, наблюдаемость | покрытие тестами (%), время сборки, метрики/алерты |
| Совместимость, портируемость | ОС/браузеры/версии API, окружения |
| Стоимость владения и эксплуатации | TCO, стоимость на 1k операций |

## Requirement quality checklist

**Этот раздел — единственный источник истины** для чек-листа качества и таблицы антипаттернов: SKILL.md и шаблоны ссылаются сюда, свои копии не ведут.

Чек-лист качества (проверять перед подтверждением):

- У каждого требования есть уникальный ID.
- Указан тип требования.
- Указан источник требования (роль, документ, user story).
- Указан приоритет (MoSCoW M/S/C/W).
- Есть критерии приёмки или способ проверки.
- Требование не противоречит другим требованиям.
- Требование измеримо и проверяемо.
- Есть связь с бизнес-целью (G-x).
- Нет неоднозначных слов: «быстро», «удобно», «качественно», «гибко» без метрик.
- Открытые вопросы вынесены отдельно (Q-01, Q-02…).
- Для NFR указаны метрика, целевое значение и бизнес-цель (G-x) — сирот-требований быть не должно.

**MoSCoW — single source of truth for the grading rules.** MoSCoW is an attribute of every requirement (BR, StR, FR, NFR, BRU) in every document; CON, ASM, DEP, INT, DAT are context, not deliverables — they are not prioritized and do not count toward the cap; RISK and GLOSS are not prioritized at all. The ≤40% cap and per-item rationale apply **only when generating the moscow document**; elsewhere the grade is a plain attribute. The cap counts deliverables only (BR, StR, FR, NFR, BRU — including NFR). It is a pragmatic guardrail, not a MoSCoW standard: classic DSDM/MoSCoW defines Must as «вмещается в таймбокс доставки» without a fixed percentage; the cap prevents Must overload — above ~40% the scope almost certainly does not fit the timebox, so push the excess down to Should/Could. Anything the user hesitates on stays Should/Could, never Must.

Каждое требование также должно быть:

- **атомарным** — одна проверяемая мысль в одном требовании;
- **однозначным** — двусмысленность уходит в GLOSS;
- **проверяемым** — есть критерий приёмки (AC) и тест-кейс (TC);
- **необходимым** — прослеживается до бизнес-цели (G);
- **осуществимым** — не противоречит CON/DEP;
- **приоритизированным** — MoSCoW (M/S/C/W);
- **трассируемым** — цепочка G → BR → FR/NFR → AC → TC.

Если требование неизмеримо — заменить на измеримое (добавить метрику и целевое значение) или вынести в открытые вопросы.

## Formats

**User story:** «Как <роль>, я хочу <действие>, чтобы <ценность>».

**Критерии приёмки (Given-When-Then):**
- Given: {{предусловие / начальное состояние}}
- When: {{действие пользователя или событие}}
- Then: {{ожидаемый результат}}

**NFR:** «Система должна <свойство> при <условие> не хуже/не более <метрика>».

## Antipatterns (не допускать)

| Антипаттерн | Почему плохо | Как исправить |
|-------------|---------------|-----------------|
| «Система должна быть удобной» | нет метрики | → NFR UX: WCAG 2.1 AA; время выполнения задачи ≤ X мин |
| «Система должна быстро работать» | нет целевого значения | → NFR: p95 latency ≤ 300 мс при нагрузке 100 RPS |
| «Пользователь может управлять всем» | нет границ и ролей | → FR с ролью, перечнем действий и прав доступа |
| «Интеграция с 1С» | нет протокола, данных, сценария, ошибок | → INT-01: протокол, состав данных, сценарий, коды ошибок |
| Смешение BR и FR в одной формулировке | разные уровни абстракции, непроверяемо | → разделить: BR (эффект) и FR (что делает система) |

## Conflicts

При конфликте требований: явно зафиксировать конфликт (что против кого), предложить ≥2 вариантов решения с trade-offs, решение фиксирует стейкхолдер. Нерешённый конфликт — открытый вопрос.

## Traceability

Trace chain: бизнес-цель (G-01) → бизнес-требование (BR-01) / user story (US-01) → FR-01, NFR-01 → критерий приёмки (AC-01) → тест-кейс (TC-01). Fan-out: one requirement may have multiple AC and TC — list them comma-separated (e.g., `AC-01, AC-02` / `TC-01, TC-02`). ID format: `<TYPE>-<NN>`.
