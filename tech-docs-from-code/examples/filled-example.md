## 1. Обзор и назначение

Сервис принимает заказы интернет-магазина, резервирует товары на складе и доводит заказ до оплаты,
публикуя события в RabbitMQ для биллинга и склада. Внешним потребителям отдаёт REST API; собственного
UI не имеет (`app/` содержит только HTTP-слой и воркеры).

**Ключевые возможности**

- Приём заказа с валидацией состава и остатков — `app/api/orders.py:31`, `app/services/order_service.py:54`
- Асинхронное подтверждение оплаты через воркер — `app/tasks/payment.py:22`
- Публикация события `order.created` после коммита транзакции — `app/services/order_service.py:88`
- Отмена заказа с компенсацией резерва — `app/services/order_service.py:131`

**Границы**

- Делает: заказы, резервы, статусы, события для смежных систем.
- Не делает: не проводит платежи (вызывает биллинг по gRPC, `app/clients/billing.py:19`), не считает
  цены каталога (получает от `catalog-api`), не отправляет уведомления клиенту.

## 2. Бизнес-логика

**Доменные сущности**

| Сущность | Роль | Код |
|---|---|---|
| `Order` | заказ клиента, носитель статуса | `app/models/order.py:18` |
| `OrderItem` | позиция заказа, фиксирует цену на момент оформления | `app/models/order.py:57` |
| `Reservation` | резерв товара на складе, живёт до отмены/оплаты | `app/models/reservation.py:11` |

**Основные сценарии**

### 2.1 Оформление заказа

1. Триггер: `POST /orders` — `app/api/orders.py:31`
2. Валидация схемы и остатков — `app/schemas/order.py:22`, `app/services/stock.py:40`
3. Резерв, расчёт суммы со скидками, запись заказа — `app/services/order_service.py:54-96`
4. После `commit` — публикация `order.created` — `app/services/order_service.py:88`
5. Ответ `202 Accepted` с `order_id`; статус меняет воркер — `app/tasks/payment.py:22`

**Правила и ограничения**

- Заказ нельзя создать без хотя бы одной позиции (`min_length=1`, `app/schemas/order.py:26`).
- Цена позиции фиксируется в `OrderItem.price` и не пересчитывается задним числом —
  `app/services/order_service.py:71`.
- Повторный `POST` с тем же `Idempotency-Key` возвращает существующий заказ —
  `app/api/deps.py:44`.
- Резерв живёт 30 минут, дальше снимается регламентной задачей — `app/tasks/expire.py:15`,
  `RESERVATION_TTL_MINUTES=30` (`app/core/config.py:41`).

**Жизненный цикл `Order`:** `new → paid → shipped → done`, ветки `failed` (ошибка оплаты) и
`cancelled` (отмена клиентом/оператором, компенсация резерва) — `app/models/order.py:24`

**Синхронно / асинхронно**

- В запросе: валидация, резерв, запись заказа, публикация события.
- В воркере: подтверждение оплаты (`orders.payment`), отгрузка (`orders.shipment`), снятие просроченных
  резервов (beat, каждые 5 минут) — `app/celery_app.py:31`.

**Диаграммы:** `docs/diagrams/business-flow.png` — процесс целиком с ветками «нет в наличии» и «оплата
не прошла»; `docs/diagrams/order-lifecycle.png` — статусы заказа.

## Что показывает этот пример

- Утверждение без якоря не пишется: «интеграция с биллингом» → `app/clients/billing.py:19`.
- Вывод из диаграммы формулируется словами («недоступность склада не блокирует приём заказа») — иначе
  диаграмма бесполезна для читателя.
- Числа (TTL, воркеры, порты) берутся из конфигов, а не из памяти.
- Секреты: в таблице конфигурации только имена (`RABBITMQ_URL`) и признак «секрет», без значений.
